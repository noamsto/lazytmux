# Remote Auth Handshake — Design Notes (#357)

## The problem

The remote probe runs with `-o BatchMode=yes` (`picker/remote.go:136`, `:287`).
Any host needing a TTY interaction therefore fails with exit 255, and
`classifyProbeErr` maps every 255 to `errRemoteUnreachable` — so a healthy host
renders as "unreachable". Measured:

```
$ ssh -o BatchMode=yes -T mbp true
Host key verification failed.          exit=255
$ ssh -o BatchMode=yes -T tp-g6 true   exit=0
```

Host-key acceptance, password auth and keyboard-interactive all collapse into
that one bucket. `mbp` — a configured `remote.hosts` entry — has been sitting
there as a false negative.

Fixing the *classification* alone would only relabel the row, because nothing
in the bridge can satisfy the interaction. `lztmux-remote-open.sh` makes 3-8
sequential `ssh` calls (lines 41, 49, 56, 78, 103, 107, 116, 121, 137) while the
bubbletea TUI holds the terminal in raw mode; the bridge daemon runs under
`setsid` with stdout to `/dev/null` and stderr to `${sock}.log`, so it has no
TTY at all. There is exactly one place a human can be asked anything, and it is
not any of those.

## Why the fix is small: `ControlMaster no` still reuses a master

The `Host *` block in `~/.ssh/config` (generated by `home/ssh/default.nix` in
nix-config) sets `ControlMaster no` with `ControlPath ~/.ssh/master-%r@%n:%p`.
`no` disables *creating* a master; it does not disable *using* one. Verified
against `tp-g6`:

```
$ ssh -o ControlMaster=yes -o ControlPersist=30 -o ControlPath=/tmp/cmtest.sock -f -N tp-g6
$ ssh -o ControlMaster=no  -o ControlPath=/tmp/cmtest.sock -v -T tp-g6 true
debug1: mux_client_request_session: master session id: 2
```

So once a master exists for a host, **every existing call site rides it with no
code change**: the probe, all eight launcher calls, the daemon's `ssh -CC`, and
the graphics fetcher (whose comment at `picker/remotebridge/graphics/fetch.go:39`
already assumes a `ControlMaster` socket that nothing in this repo creates).

The only missing piece is master *creation*. That is the whole feature.

`ssh -G <host>` resolves `controlpath` to
`/home/noams/.ssh/master-noams@mbp:22` — comfortably under the 108-byte
`sun_path` limit, which a longer path silently blows (`unix_listener: path … too
long for Unix domain socket`).

## Probe classification: two new states

`classifyProbeErr` currently takes `(err, timedOut)`. Neither probe captures
stderr at all — `cmd.Stderr` is left nil and discarded. Both gain a stderr
buffer, and the classifier becomes
`classifyProbeErr(err error, stderr string, timedOut bool) error`, returning two
new sentinels alongside the existing pair: `errRemoteNeedsAuth` and
`errRemoteHostKeyChanged`, surfaced as `remoteProbeNeedsAuth` and
`remoteProbeHostKeyChanged`.

Patterns are matched in this order:

1. **`REMOTE HOST IDENTIFICATION HAS CHANGED`** → `errRemoteHostKeyChanged`
   (see below). Checked first because it is the dangerous one.
2. **`Host key verification failed`**, **`Permission denied`**, **`Too many
   authentication failures`**, **`keyboard-interactive`** → `errRemoteNeedsAuth`.
3. Anything else → `errRemoteUnreachable`, unchanged.

Non-255 exits keep mapping to `errRemoteNoServer` exactly as today — that logic
is untouched, since a non-255 status means the remote command itself ran.

Rule 3 as the default matters: an unrecognised 255 keeps today's behaviour
rather than inviting the user into an auth flow that cannot help. Being wrong
in the direction of "unreachable" costs a stale label; being wrong toward
"auth needed" costs a pointless password prompt.

### A *changed* host key is not an auth prompt

`REMOTE HOST IDENTIFICATION HAS CHANGED` means the host key no longer matches
`known_hosts`. That is the signature of a MITM as much as of a reinstalled
host, and resolving it requires a human comparing fingerprints out of band.

So it gets its own state and its own row, and **Enter does nothing on it**:

```
mbp    (host key changed — verify manually)
```

The auth popup must never be reachable from this state. A flow that offers
"Enter to connect" here would train the user to accept a key change without
looking, which is precisely the check the warning exists to force.

## Where the interactive prompt runs

The picker already runs inside `display-popup -E` (`scripts/tmux-session-picker.sh`,
bound at `config/tmux.conf.nix:746` via `run-shell`). A nested `display-popup`
would be a second popup on the same client, so the prompt goes in the popup we
already have: **`tea.ExecProcess`**, which releases the terminal, runs the child
against the real pty, and restores bubbletea afterwards.

Verified present in the pinned version — `charm.land/bubbletea/v2 v2.0.2`,
`exec.go:50`: `func ExecProcess(c *exec.Cmd, fn ExecCallback) Cmd`. The picker
does not use it anywhere yet, so this is the first instance.

This keeps the whole interaction inside the popup the user already opened, and
means ssh — not lazytmux — owns the terminal while a secret is typed.

**To verify during implementation:** that a popup pane's pty survives
`ExecProcess` release/restore cleanly. The popup is an ordinary tmux pane, so it
should, but it is untested here and the failure mode (a corrupted popup, or ssh
unable to open `/dev/tty`) is visible enough to catch immediately.

## The master command

A new script, `lztmux-remote-auth <host>`:

```bash
ssh -M -f -o ControlPersist=<authPersistSeconds> -o ServerAliveInterval=15 <host> true
```

- `-M` creates the master, overriding the config's `ControlMaster no`.
- **No `-o ControlPath`.** The config's path must win, or the master lands
  somewhere the other call sites do not look.
- **No `BatchMode`.** The entire point is to allow the prompt.
- `-f` backgrounds *after* authentication, so the host-key question and the
  password prompt are both in the foreground with the tty, and the command
  returning is itself the signal that auth succeeded.
- `true` rather than `-N`: with a trivial command plus `ControlPersist`, the
  master self-reaps. Verified with `ControlPersist=5` — master alive at 0s,
  process *and* socket file both gone at 9s. `-N` instead lives forever until an
  explicit `-O exit`, and leaves a stale socket across a suspend.
- `-o ServerAliveInterval=15` because `Host *` sets it to `0`. See below.

## Offering the key: one prompt, ever

After the master is up, test whether pubkey auth *alone* would have worked,
bypassing the master:

```bash
ssh -o BatchMode=yes -o ControlPath=none <host> true
```

`ControlPath=none` forces a fresh connection rather than riding the master we
just made; `BatchMode=yes` makes it fail instead of prompting. Non-zero exit
means the key is not installed. This tests the condition directly rather than
parsing `ssh -v` for `Authenticated to … using "password"`.

If it fails, the same popup asks:

```
Install ~/.ssh/id_ed25519.pub on mbp so this is the last time? [y/N]
```

On `y`, run `ssh-copy-id -i <key> <host>`, which rides the master and so needs
no second password.

The key **must** come from `ssh -G <host> | awk '$1=="identityfile"'`, never a
hardcoded default: this machine has both `id_ed25519` and
`noam_factify_ed25519`, and a work key must not land on a personal host. `ssh -G`
resolves it per host (`identityfile ~/.ssh/id_ed25519` for both `mbp` and
`tp-g6`).

A declined offer is not recorded anywhere: the probe above is the only gate, so
the question reappears on the next manual auth and stops for good the moment the
key is installed by any means.

**To verify during implementation:** that `ssh-copy-id` actually reuses the
master. It is `ssh` underneath and reads the same config, so it should, but this
was deliberately not tested during design because confirming it means writing to
a real host's `authorized_keys`. `ssh-copy-id -n` (dry run) is available for
checking the mechanism without mutating anything.

## Master staleness

`Host *` sets `ServerAliveInterval 0`, so keepalives are off and a master whose
network dropped can sit alive-but-hung. `ssh -O check` does not catch this: it
is local IPC to a master process that is still running. It catches only the
*dead* master — socket file present, process gone.

Two consequences:

- The master invocation carries its own `-o ServerAliveInterval=15`, so a
  half-open master terminates itself rather than hanging every later call.
- `remoteSessionsForHost` gains a pre-probe gate: if the resolved `controlpath`
  exists, `ssh -O check` runs first (local IPC, no network, effectively
  instant); on failure the stale socket is removed and the host is reported as
  `remoteProbeNeedsAuth` without paying the 3s probe timeout. This handles
  suspend-then-resume, the common case.

`ControlPersist` is an **idle** timer — it starts counting only once no
multiplexed sessions remain. The daemon's `ssh -CC` is a session riding the
master for the life of the mirror, so a live bridge never idles out regardless
of how short `authPersist` is. The timer effectively measures time since the
last bridged session to that host closed.

## The `authPersistSeconds` option

`programs.lazytmux.remote.authPersistSeconds`, default `14400` (4h), clamped to
`60`-`86400` — the same integer-seconds-with-a-clamp shape as
`prRefreshSeconds` and `splash.timeout`, rather than a duration string. ssh
accepts a bare number of seconds for `ControlPersist`, so the value passes
through untransformed, and a clamp on an integer is meaningful in a way a clamp
on `"4h"` would not be.

No per-host configuration: the needs-auth state is discovered from the probe, so
a host needs no declaration beyond already being in `remote.hosts`.

## Testing

- **`classifyProbeErr` is pure** given `(err, stderr, timedOut)` — a table test
  over real captured stderr strings, including the host-key-changed case, is the
  bulk of the coverage and runs under `nix flake check`.
- **The row rendering** follows the existing `(no server — Enter starts one)`
  pattern and is testable the same way, including that the host-key-changed row
  is Enter-inert.
- **The popup path is not unit-testable** — it needs a real tty and a real host.
  It gets hardware verification against `mbp`, which is the host that motivated
  the issue: probe shows the auth row, Enter accepts the key and takes the
  password, the bridge opens, and a second `prefix + s` shows the host green
  with no interaction.

## Rejected: persisting the password

Storing the password, encrypted or otherwise, was considered and rejected.

For the detached daemon to use a stored password unattended, lazytmux must
decrypt it unattended — so the decryption key has to be available unattended,
next to the ciphertext. That is obfuscation, not encryption: anything that can
read `~` reads both. Gating decryption on a user interaction removes the
problem and also removes the benefit, since that is another prompt.

There is additionally no credential store in use on this machine to delegate to
— `secret-tool` and `pass` are absent, `kwalletd6` is absent, and
`gnome-keyring-daemon` is installed but its service is inactive. Doing this
properly would mean lazytmux inventing its own secret store, which is the wrong
layer for a tmux configuration.

The `ssh-copy-id` offer removes the motivation outright: with a key installed
the password is asked for once, ever, and nothing is stored by lazytmux at any
point. An `SSH_ASKPASS` helper backed by a real OS keychain remains the escape
hatch if a host ever turns up that cannot accept a key — but it is not built
here, and should not be until such a host exists.

## Out of scope

- `SSH_ASKPASS` in any form (above).
- Auto-reauthentication when a master dies mid-session. The `-O check` gate plus
  the needs-auth row means the user is told to reconnect; the bridge does not
  try to repair itself. Revisit only if a master proves to die often in practice.
- Anything about the eight launcher calls or the daemon. They are unchanged, and
  that is the design's main claim.
